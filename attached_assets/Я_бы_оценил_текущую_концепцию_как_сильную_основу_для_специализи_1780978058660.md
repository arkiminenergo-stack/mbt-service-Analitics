Я бы оценил текущую концепцию как сильную основу для специализированной системы документального анализа, но пока она больше похожа на набор функций, чем на действительно универсальную платформу проверки документов.

## Что уже сделано правильно  
Самое сильное решение — отказ от полного доверия LLM.  
Большинство современных систем пытаются анализировать документы исключительно через нейросети, что приводит к:  
* галлюцинациям;  
* невозможности аудита результатов;  
* нестабильности;  
* юридическим рискам.  
У вас же:  
```
LLM → конфигурирует
Алгоритмы → выполняют
Пользователь → утверждает

```
Это правильная архитектура для:  
* государственных органов;  
* энергетики;  
* судебных процессов;  
* аудита;  
* контрольно-надзорной деятельности.  
   
⸻  
   
## Главная проблема  
Сейчас система ориентирована на документ.  
На практике заказчики покупают не анализ документов.  
Они покупают решение бизнес-задачи.  
Например:  
* проверка исполнительной документации;  
* проверка договорного пакета;  
* проверка заявки на субсидию;  
* проверка разрешительной документации;  
* проверка земельных работ;  
* проверка проектной документации.  
Поэтому я бы изменил базовую сущность.  
Сейчас:  
```
Проект
 └ Документы

```
Предлагаю:  
```
Кейс
 ├ Документы
 ├ Правила проверки
 ├ Требования
 ├ Связанные объекты
 ├ Проверки
 └ Отчеты

```
   
⸻  
   
## Чего критически не хватает  
## 1. Движка правил проверки  
Сейчас система извлекает данные.  
Но заказчику нужен ответ:  
“Документ соответствует требованиям или нет?”  
Нужен полноценный Rule Engine.  
Пример:  
```
{
  "rule": "contract_date_before_invoice",
  "if": {
    "invoice_exists": true
  },
  "check": {
    "contract_date": "< invoice_date"
  },
  "severity": "critical"
}

```
Тогда система сможет автоматически выявлять:  
* ошибки;  
* нарушения;  
* противоречия;  
* отсутствие обязательных документов.  
Именно это превращает OCR-систему в систему контроля.  
   
⸻  
   
## 2. Онтология предметной области  
Сегодня:  
```
Документ

```
Завтра:  
```
Контрагент
Объект
Сеть
Подстанция
Земельный участок
Судебное дело
Договор
Исполнитель

```
Нужен слой сущностей.  
   
Например:  
```
Документ №123

из него извлечено:

ООО Ромашка
ИНН 123456
Договор №77
Подстанция ПС-110

```
Все эти сущности должны жить отдельно от документа.  
Тогда появляется граф знаний.  
   
⸻  
   
## 3. Проверка полноты пакета  
Это огромный коммерческий кейс.  
Например:  
Для договора должны существовать:  
* договор;  
* приложение;  
* спецификация;  
* акт;  
* счет.  
Если чего-то нет:  
```
Не найдено приложение №2

```
Для госуслуг это вообще золотая функция.  
   
⸻  
   
## 4. Версионность документов  
Часто приходят:  
```
Договор_v1
Договор_v2
Договор_final

```
Система должна понимать:  
* это один документ;  
* какие пункты изменились;  
* какие суммы изменились;  
* кто изменил.  
Это отдельный модуль.  
   
⸻  
   
## Что бы я добавил для Минэнерго  
Учитывая ваш профиль проектов цифровой трансформации в энергетике.  
Добавил бы объектную модель:  
```
Энергетический объект
 ├ Подстанция
 ├ ЛЭП
 ├ ТП
 ├ Газопровод
 ├ Котельная
 └ Теплотрасса

```
И привязку документов к объектам.  
Тогда система сможет отвечать:  
Покажи все документы по данной подстанции за последние 5 лет.  
или  
Какие аварии происходили на этом объекте?  
или  
Какие земляные работы проводились рядом с данным участком сети?  
Это уже уровень цифрового двойника документации.  
   
⸻  
   
## Что бы я убрал  
Не стал бы делать агента центральной сущностью.  
Сейчас многие системы строят так:  
```
Чат → вызывает инструменты

```
На практике через год пользователи почти перестают пользоваться чатом.  
Они используют:  
* кнопки;  
* шаблоны;  
* автоматические сценарии.  
Поэтому агент должен быть:  
```
Вторичный интерфейс

```
а не основной.  
   
⸻  
   
## Оптимальная целевая архитектура  
Я бы строил систему в 5 слоях:  
```
1. Документы
    ↓
2. Извлечение данных
    ↓
3. Нормализация сущностей
    ↓
4. Движок правил
    ↓
5. Отчеты и рекомендации

```
где ИИ используется только для:  
* классификации;  
* извлечения сложных сущностей;  
* генерации правил;  
* объяснения результатов.  
   
⸻  
   
## Самое перспективное направление  
Если смотреть на рынок 2026–2030 годов, наибольшую ценность даст не OCR и не чат.  
Наибольшую ценность даст автоматическая экспертиза пакетов документов.  
То есть система должна отвечать не:  
“Вот данные из документов”  
а:  
“Пакет соответствует требованиям на 87%. Отсутствуют 3 документа. Найдено 5 противоречий. Обнаружены 2 критических нарушения.”  
В этот момент продукт превращается из системы хранения документов в систему принятия решений, а это уже существенно более дорогой класс решений для государства, энергетики, строительства, аудита и юридического сопровождения.  
  
Первая задача - организация проверки документов для заявки на субсидию.  
  
Проанализируй [https://mosoblpravo.ru/postanovlenie/2026/04/17/n-429-pp/](https://mosoblpravo.ru/postanovlenie/2026/04/17/n-429-pp/)  
  
И адаптируй систему для проверки документации для субсидирования. Предложи, какие функции необходимо заложить в систему. Помни, мы делаем универсальную систему, проверка комплекта документации - один из вариантов использования.  
  
После анализа постановления №429-ПП видно интересную вещь.  
Само постановление не описывает детально процедуру проверки заявителя на субсидию. Оно задает требования к пакету документов, основания для финансирования, перечень подтверждающих документов и контроль результативности.    
Поэтому для проектирования системы важно смотреть не на конкретный комплект документов, а на саму логику принятия решения.  
Именно эта логика позволит сделать платформу универсальной.  
   
⸻  
   
## Что фактически проверяет ведомство  
Если разложить постановление на смысловые блоки, получается:  
**Блок 1. Право на участие**  
Есть ли у заявителя право претендовать на субсидию?  
Например:  
* муниципалитет входит в программу;  
* объект относится к теплоснабжению;  
* есть решение штаба;  
* есть полномочия заявителя.  
   
⸻  
   
**Блок 2. Полнота пакета**  
Предоставлены ли все обязательные документы?  
Например:  
* заявка;  
* сметный расчет;  
* документы на объект;  
* выписка ЕГРН;  
* договор аренды.  
   
⸻  
   
**Блок 3. Логическая согласованность**  
Нет ли противоречий между документами?  
Например:  
* объект в заявке совпадает с объектом в ЕГРН;  
* правообладатель совпадает;  
* адрес совпадает;  
* стоимость совпадает со сметой.  
   
⸻  
   
**Блок 4. Финансовая проверка**  
Соответствует ли финансирование правилам?  
Например:  
* смета корректна;  
* не превышены лимиты;  
* размер субсидии рассчитан верно.  
   
⸻  
   
**Блок 5. Проверка факта выполнения**  
После получения средств:  
* акты КС-2;  
* КС-3;  
* УПД;  
* счета-фактуры;  
* платежные поручения;  
* акты приемки.  
   
⸻  
   
**Блок 6. Проверка достижения результата**  
Самая важная часть.  
В постановлении фигурирует целевой показатель:  
количество объектов теплоснабжения, по которым выполнен капитальный ремонт.    
То есть государство проверяет не документы.  
Оно проверяет достижение результата.  
   
⸻  
   
## Из этого следует ключевой вывод  
Система должна проверять не документы.  
Она должна проверять:  
```
Требование
    ↓
Доказательства
    ↓
Решение

```
Документы являются лишь доказательствами.  
   
⸻  
   
## Предлагаемая универсальная архитектура  
Я бы построил платформу вокруг сущности:  
```
Проверка (Case)

```
а не вокруг документа.  
   
⸻  
   
## Сущность 1. Программа поддержки  
Например:  
```
Субсидия на капремонт теплоснабжения
Грант для МСП
Компенсация затрат
Лизинговая поддержка

```
Каждая программа содержит правила.  
   
⸻  
   
## Сущность 2. Требование  
Пример:  
```
Требование:
Объект должен находиться
в собственности
или аренде заявителя

```
Источник:  
* постановление;  
* приказ;  
* регламент.  
   
⸻  
   
## Сущность 3. Доказательство  
Какие документы подтверждают требование:  
```
ЕГРН
или
Договор аренды

```
   
⸻  
   
## Сущность 4. Правило проверки  
Например:  
```
Если
ЕГРН отсутствует

и

Договор аренды отсутствует

то

ошибка критическая

```
   
⸻  
   
## Какие функции заложить в систему  
## 1. Конструктор регламентов  
Самый важный модуль.  
Без программирования.  
Пример:  
```
Добавить требование

Название:
Право собственности

Подтверждается:
- Выпиской ЕГРН
- Договором аренды

Тип проверки:
обязательное

```
После этого новая субсидия настраивается без разработки.  
   
⸻  
   
## 2. Конструктор комплектов документов  
Пример:  
```
Для заявки нужны:

✓ заявление
✓ смета
✓ ЕГРН
✓ решение комиссии

```
Система автоматически определяет:  
```
Получено 3 из 4

Отсутствует:
решение комиссии

```
   
⸻  
   
## 3. Извлечение сущностей  
Из любых документов:  
```
ИНН

ОГРН

Адрес

Кадастровый номер

Сумма

Дата

Объект инфраструктуры

Контрагент

```
Это будет база для любых проверок.  
   
⸻  
   
## 4. Междокументная сверка  
Критически важный модуль.  
Пример:  
```
Заявка

Адрес:
ул. Ленина 10

ЕГРН

Адрес:
ул. Ленина 12

```
Результат:  
```
Несоответствие адреса

```
   
⸻  
   
## 5. Проверка полномочий  
Очень востребовано для госорганов.  
Например:  
```
Подписант договора

=
директор организации

```
или  
```
есть доверенность

```
   
⸻  
   
## 6. Проверка сроков  
Например:  
```
Справка не старше 30 дней

Договор действует на дату подачи

Лицензия не просрочена

```
   
⸻  
   
## 7. Проверка финансовой модели  
Для субсидий это отдельный класс задач.  
Проверка:  
```
смета

лимиты

процент софинансирования

максимальная сумма

```
   
⸻  
   
## 8. Проверка достижения результата  
Самый недооцененный модуль.  
После выдачи субсидии система должна проверять:  
```
Что обещали

Что сделали

Что оплатили

Что приняли

```
И показывать расхождения.  
   
⸻  
   
## 9. Интеграция с государственными реестрами  
Для автоматической верификации:  
* ЕГРН;  
* ЕГРЮЛ;  
* ФНС;  
* ГИС ЖКХ;  
* ГИС ТОР КНД;  
* казначейство;  
* региональные ГИС.  
Тогда половина документов вообще не потребуется.  
   
⸻  
   
## 10. Генератор заключения  
На выходе не отчет.  
На выходе решение.  
Например:  
```
Статус:
Условно одобрено

Полнота пакета:
96%

Критические замечания:
2

Некритические замечания:
7

Рекомендуемое решение:
запросить доработку

```
   
⸻  
   
## Если смотреть на перспективу  
Я бы проектировал систему как универсальный движок нормативного контроля.  
Тогда субсидии будут лишь одним из сценариев.  
На той же платформе можно реализовать:  
* субсидирование;  
* гранты;  
* госзакупки;  
* экспертизу проектной документации;  
* контроль инвестиционных программ;  
* проверку аварийных заявок;  
* согласование земляных работ;  
* контроль исполнения поручений;  
* проверку отчетности ресурсоснабжающих организаций.  
Фактически это будет не “система проверки документов”, а **Low-Code платформа цифровой экспертизы и принятия решений на основе регламентов**, где документы являются только одним из источников доказательств для проверки требований.  
  
Опиши максимально подробно архитектуру универсальной платформы цифровой экспертизы.  
  
Если проектировать систему не как “проверку документов”, а как платформу цифровой экспертизы для государства, энергетики, строительства, грантов, субсидий, закупок и контроля исполнения программ, то архитектура должна быть значительно шире.  
По сути это должна быть система, которая отвечает на вопрос:  
Соответствует ли рассматриваемый объект требованиям нормативной базы и можно ли принять положительное решение?  
   
⸻  
   
## Концептуальная модель  
Любая экспертиза состоит из пяти сущностей:  
```
Нормативное требование
        ↓
Доказательства
        ↓
Проверки
        ↓
Выявленные факты
        ↓
Решение

```
Например:  
```
Требование:
У заявителя отсутствует задолженность

Доказательства:
справка ФНС

Проверка:
задолженность = 0

Факт:
условие выполнено

Решение:
допустить

```
Именно вокруг этой модели должна строиться вся система.  
   
⸻

```
│ Пользовательские интерфейсы  │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│ Оркестратор процессов        │
└──────────────┬───────────────┘
               │
 ┌─────────────┼─────────────┐
 │             │             │
 ▼             ▼             ▼

 Документы   Реестры      Внешние ИС

 │             │             │

 ▼             ▼             ▼

 Слой извлечения данных

 ▼

 Граф сущностей

 ▼

 Движок правил

 ▼

 Движок принятия решений

 ▼

 Отчеты и заключения

```
   
⸻  
   
## Слой 1. Управление кейсами  
Главная сущность системы.  
Не документ.  
Не заявка.  
А кейс.  
```
Кейс
 ├ Тип проверки
 ├ Объект проверки
 ├ Участники
 ├ Документы
 ├ Проверки
 ├ Заключения
 └ История

```
Примеры:  
```
Кейс №1
Субсидия

Кейс №2
Госзакупка

Кейс №3
Земельные работы

Кейс №4
Инвестпрограмма

Кейс №5
Авария

```
   
⸻  
   
## Слой 2. Универсальное хранилище доказательств  
Любая информация должна храниться одинаково.  
Не важно:  
* PDF;  
* DOCX;  
* XLSX;  
* XML;  
* JSON;  
* письмо;  
* данные реестра;  
* данные GIS.  
Все превращается в:  
```
{
  "source": "...",
  "type": "...",
  "attributes": {}
}

```
То есть документ становится просто источником фактов.  
   
⸻  
   
## Слой 3. Интеллектуальное извлечение данных  
Задача:  
получить структуру из неструктурированных данных.  
Например:  
Из договора:  
```
ООО Альфа

ИНН

сумма

срок

объект

```
Из сметы:  
```
позиции
объемы
стоимость

```
Из схемы:
